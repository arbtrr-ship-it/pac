# PAC — Product Architecture Copilot · Спецификация продукта

> Документ описывает **идею продукта**, его архитектуру, пользовательские сценарии и бизнес-логику.
> Технические соглашения и правила разработки — в [`CLAUDE.md`](./CLAUDE.md).

---

## 1. Идея продукта

**PAC (Product Architecture Copilot)** — это «AI Head of Product»: ассистент, который помогает
продуктовым менеджерам принимать **приоритетные решения в контексте стратегии**, а не изолированно.

Любая инициатива (фича, эксперимент, рефакторинг) прогоняется через единую модель оценки и
получает вердикт `Now / Next / Later / Reject` с объяснением — почему именно так.

```
        ┌──────────────────────────────────────────────────────────┐
        │  «У меня есть идея фичи. Делать её сейчас, потом или нет?» │
        └──────────────────────────────────────────────────────────┘
                                   │
                                   ▼
        ┌──────────────────────────────────────────────────────────┐
        │   PAC: оценка в контексте стратегии квартала              │
        │   fit · impact · complexity · confidence  →  вердикт      │
        └──────────────────────────────────────────────────────────┘
                                   │
                                   ▼
            Now ───── Next ───── Later ───── Reject   + причинная цепочка
```

## 2. Проблема и решение

| Проблема PM-а | Что делает PAC |
|---|---|
| Идеи копятся хаотично, приоритизация «по интуиции» | Единая скоринговая модель с прозрачной формулой |
| Решения принимаются в отрыве от стратегии квартала | Каждая гипотеза сверяется с фокусом, anti-focus и целевой метрикой |
| Неясно, как фича влияет на бизнес-метрику | Строится причинно-следственная цепочка «инициатива → метрика» |
| Roadmap перегружен, фокус размыт | Алерты о перегрузе и перекосах, индекс зрелости (PAS) |
| Нет «второго мнения» по пробелам | AI Product Office находит слепые зоны и генерирует инициативы |

**Суть решения:** превратить приоритизацию из спора мнений в воспроизводимый
аналитический процесс, где каждое решение прослеживается до стратегии.

---

## 3. Целевая аудитория

- **Product Managers** — нужна структура для ежедневной приоритизации гипотез.
- **CPO / Heads of Product** — нужен обзор зрелости продуктовой архитектуры и баланса roadmap.
- Контекст использования: планирование квартала, груминг бэклога, стратегические ретро.

---

## 4. Ключевая ценность

1. **Контекстность** — оценка инициативы всегда привязана к сохранённой стратегии (версии).
2. **Прозрачность** — виден не только вердикт, но и разложение по компонентам формулы.
3. **Причинность** — явно фиксируются слабые звенья в логике «фича → бизнес-результат».
4. **Скорость** — весь цикл «идея → вердикт → roadmap» проходится за минуты, без внешних инструментов.

Приложение полностью клиентское — один HTML-файл, без бэкенда, без сборки, без зависимостей-пакетов.

```

│   │  HTML-разметка │  CSS (<style>) │  JS-логика (<script>)     │    │
│   │  4 таба + modal│  Custom Props  │  state + rule-based «AI»  │    │
│   └───────────────┴────────────────┴───────────────────────────┘    │
│                              │                                      │
│                              ▼                                      │

            │                                    ▲
```

## 9. Функциональные блоки (4 таба)

### Таб 1 — Стратегия
Мастер из 3 шагов, формализует контекст продукта:
- **Шаг 1 · Продукт** — название, категория, описание, ценность, аудитория.
- **Шаг 2 · Стратегия** — целевая метрика + baseline/target/дедлайн; фокус и доп. фокус;
  **anti-focus** (зоны, которые НЕ усиливаются); ограничения (стадия, ресурс, бюджет, темп, dev-мощность).
- **Шаг 3 · Стратегические гипотезы** — причинно-следственные утверждения «что мы считаем истиной» (опционально).
- Сохранение создаёт **версию стратегии** (`v1`, `v2`, …) — история неизменяема.

### Таб 2 — Гипотеза
- Готовые идеи-чипы, сгенерированные под фокус / anti-focus / категорию продукта.
- Поле для своей инициативы.
- `Проанализировать` → скоринг + анализ в **3 слоях**:
  - **Стратегический** — конфликты с anti-focus, причинная цепочка, слабые звенья.
  - **Архитектурный** — уровень риска, перегруз команды/Now-колонки.
  - **Экономический** — влияние на LTV/CAC, Cost of Delay, Cost of Implementation.
- 3 варианта реализации: **Lean / Experiment / Full**.
- Глубина анализа: **Quick / Standard / Deep** (зависит от impact и сложности).

### Таб 3 — Roadmap
- Доска из 4 колонок: **Now / Next / Later / Reject**, поддержка drag & drop.
- Карточка инициативы: текст, fit/confidence, метка `AI`/`User`, версия стратегии.
- **История решений** — хронология, клик открывает модалку с полным анализом и контекстом стратегии.
- **Алерты** — перегруз Now (>3), стратегический перекос (≥70% в одной колонке).
- **Снимок архитектуры** — сводка по продукту, PAS, распределению.

### Таб 4 — AI Office
- **Системные инициативы** — PAC находит пробелы: непокрытый фокус, слепые зоны, перегруз, перекос.
- **Product Architecture Score** — индекс зрелости с разложением по компонентам.
- **Ретроспектива** — список версий стратегии с привязкой гипотез.

## 10. Бизнес-логика

### 10.1 Скоринговая модель — `scoreHypothesis()`

Текст инициативы анализируется поиском **русских ключевых подстрок** и даёт 4 параметра (0–5):

| Параметр | Как считается |
|---|---|
| **Strategic Fit** | `focus_match` (0–2) + `anti_focus_penalty` (−2…0) + `metric_alignment` (0–2) + `constraint_feasibility` (0–1) |
| **Impact** | `2 + число совпадений` с keyword-ами роста/масштаба/выручки |
| **Complexity** | По числу «тяжёлых» технических слов и длине описания |
| **Confidence** | Качество гипотезы: наличие механизма (`потому что`, `за счёт`…), измеримой метрики, отсутствие размытости |

**Правила вердикта:**

```
fit ≥ 4  и  complexity ≤ 3   →  NOW
fit ≥ 3                      →  NEXT
fit = 2                      →  LATER
иначе                        →  REJECT
```

> ⚠️ Веса и пороги — ядро продукта. Менять только с пониманием бизнес-логики.
> Скоринг завязан на русские ключевые слова: смена формулировок в UI незаметно ломает оценку.

### 10.2 Причинно-следственные цепочки — `buildCausalChain()`

Строит цепочку и явно фиксирует слабые звенья:

```
  Инициатива  ──►  Поведение  ──►  Промежуточная  ──►  Целевая
                  пользователя       метрика            метрика
   (что делаем)   (что изменится)   (Activation rate,   (MRR, Retention…)
                                     Viral coef…)
                          │
                          └─►  ⚠️ Weak links: нет механизма / нет метрики /
                                  попадание в anti-focus / низкий confidence
```

### 10.3 Пять стратегических фокусов (AARRR)

`Acquisition · Activation · Retention · Monetization · Infrastructure` —
вокруг них строится вся система: генерация идей, keyword-ы скоринга, поиск пробелов в AI Office.

### 10.4 Product Architecture Score (PAS)

Составной индекс **0–100**, взвешенная сумма 5 компонентов:

| Компонент | Вес | Что отражает |
|---|---|---|
| Распределение | 0.25 | Нет ли перекоса по колонкам roadmap |
| Связка с метрикой | 0.20 | Доля инициатив с confidence ≥ 4 |
| Качество причинных цепочек | 0.20 | Доля инициатив с механизмом или метрикой |
| Здоровье Now | 0.20 | Не перегружена ли колонка Now |
| Средний Strategic Fit | 0.15 | Насколько инициативы попадают в стратегию |

Пороги: **70+ зелёный · 45–69 жёлтый · <45 красный**.

### 10.5 AI Product Office — `runAIOffice()`

Rule-based аудит roadmap: считает покрытие по 5 фокусам и генерирует замечания —
непокрытый фокус квартала (high), слепые зоны вне anti-focus (medium),
перегруз Now (high), перекос ≥65% в одно направление (medium).

> Все «AI»-фичи (`generateSuggestions`, `buildCausalChain`, `runAIOffice`) —
> **шаблонная генерация по ключевым словам**, никакого ML или внешнего API.

## 11. Модель данных (in-memory state)

```
product            { name, category, desc, value, audience }
        │
        ▼
strategy           { version, ts, product, targetMetric, baseline/target/date,
        │            focus, focus2, antiFocus[], stage, resource, budget,
        │            tempo, devCap, stratHyps[] }
        │
strategyVersions[] ─ неизменяемая история стратегий (v1, v2, …)
        │
        ▼
analysis           { text, scores{fit,impact,complexity,confidence,verdict,depth},
        │            causal{action,behaviour,interMetric,targetMetric,weakLinks},
        │            alts[], conflictHtml }
        │
        ▼
roadmap            { now[], next[], later[], reject[] }  ← item = analysis + id + zone + ctx
history[]          ─ все добавленные инициативы (для модалки и PAS)
pasScore           ─ число 0–100
```

Каждый item в roadmap хранит **снимок стратегии** на момент добавления (`stratCtx`) —
поэтому исторические решения остаются объяснимыми даже после смены стратегии.

## 12. Технологический стек

- **Vanilla JavaScript (ES6+)** — без фреймворков, без npm, без build-step.
- **Vanilla CSS** — CSS Custom Properties, Grid, Flexbox.
- **HTML5** — единый файл-приложение.
- **Netlify** — хостинг статики, SPA-редиректы через `_redirects`.
- **Google Fonts** — Syne, DM Sans, DM Mono (через CDN).

---

## 13. Ограничения и не-цели (non-goals)

- ❌ **Нет персистентности** — состояние сбрасывается при перезагрузке (намеренно для MVP/demo).
- ❌ **Нет реального AI/ML** — вся «интеллектуальность» это rule-based шаблоны.
- ❌ **Нет бэкенда, аккаунтов, коллаборации** — приложение однопользовательское и клиентское.
- ❌ **Нет сборки и зависимостей** — ценность проекта в отсутствии этого усложнения.
- ❌ **UI только на русском** — ключевые слова скоринга завязаны на русские подстроки.
